# 2026-07-26 阶段复盘与版本存档

## 当前版本定位

联结宇宙小程序已经从单一 Agent 展示，进入到「需求 / 服务 / 找人 / 我的」并行的内测版本。

当前核心判断：
- 需求是社区连接的第一入口，代表用户此刻正在寻找什么。
- 服务是可交付价值的入口，代表用户能解决什么问题。
- 找人是身份档案与匹配报告入口，代表谁值得进一步了解。
- 我的 Agent 是用户自己的数字档案和经营工作台，不再承担首页主叙事。
- 社区动态由后台运营发布，首页首屏不再重复展示个人档案。

## 当前用户路径复盘

### 首页

首页应该回答一个问题：今天社区里有什么值得我看？

当前结构基本正确：
- 第一眼看社区动态。
- 第二步给用户一个当前最该完成的动作。
- 再往下进入需求、服务、Agent、推荐等列表。

后续优化方向：
- 首页不宜承载太多解释性内容。
- 社区动态每屏控制在 3-6 条，避免用户感觉信息拥挤。
- 首页最好逐步加入「最新需求」「本周可预约服务」「新成员」三类摘要，但每类只给 1-2 个代表。

### 找需求

找需求应优先解决：谁正在找什么，我是否能帮。

当前风险：
- 需求仍存储在 `agents.agent_config.demand_posts` 内，不是独立表。
- 后台虽然能管理需求，但长期会限制搜索、推荐、状态统计和运营分析。

建议：
- 下一阶段把需求迁移为独立 `demands` 表。
- 每条需求应有：标题、描述、预算或交换方式、截止时间、领域标签、状态、解决记录。

### 找服务

找服务应优先解决：这个服务帮我解决什么问题，适不适合我，交付边界是什么。

当前结构已明显改善：
- 服务详情开始接近一个服务落地页。
- 服务表单已补充适合人群、交付物、案例描述。

后续优化方向：
- 服务描述现在仍主要拼接在 `description` 字段里。
- 下一阶段应把服务扩展字段独立成结构化字段，避免后期解析文本。

### 找人 / Agent 广场

找人应优先解决：这个人有什么价值、当前需要什么、我为什么要联系。

当前结构基本成立：
- 公开档案、需求、服务数量、匹配入口都有了。

后续优化方向：
- Agent 卡片需要更强的首要信号：当前需求优先，其次服务能力，再次经历。
- 匹配按钮应保持轻量，不压过内容本身。

### 我的 Agent

我的 Agent 应是用户自己的经营工作台。

当前栏目结构是正确的：
- 档案：价值呈现。
- 需求：发布个人动态式需求。
- 服务：发布和修改可交付项目。
- 技能：能力开关。
- 信任：关系与履约沉淀。
- 匹配：历史报告和指定匹配。

后续优化方向：
- 每个栏目顶部增加一句非常短的行动导向提示。
- 保存后的状态反馈要更明显。
- 对未登录、登录失效、网络失败需要统一空状态。

### 匹配报告

匹配报告应回答：为什么匹配、适合怎么开始、不适合在哪里。

当前报告比早期更聚焦，但仍有优化空间：
- 评分算法仍偏规则和文本重合，缺少真实行为数据。
- 建议应继续减少抽象词，增加具体动作。

下一阶段建议：
- 报告结构固定为：匹配类型、关键证据、风险边界、三步行动。
- 不再展示冗长摘要。
- 支持从一次匹配报告直接进入：发起沟通、预约服务、保存为关注对象。

## 已知风险

### P0：微信登录配置仍需持续验证

原因：
- 管理员无法登录曾经出现过，体验者可以登录。
- 真实微信登录依赖 AppID、AppSecret、体验者权限、开发者工具 AppID 一致性。

处理建议：
- 发布前固定做一次管理员与体验者双账号登录测试。
- 后台保留 `dev_mode` 只用于开发，不作为真实内测路径。

### P1：需求数据应独立建表

当前需求放在 Agent JSON 配置中，短期可用，长期不利于筛选、统计、推荐和权限控制。

建议下一阶段优先做：
- `demands` 表。
- 用户端发布 / 编辑需求改为独立 API。
- 老数据从 `agent_config.demand_posts` 平滑迁移。

### P1：服务详情结构化不足

适合人群、交付物、案例描述目前主要通过描述文本承载。

建议：
- 新增服务扩展字段或 `service_config` JSON 字段。
- 前端不再依赖文本分段解析。

### P1：匹配报告缺少真实互动闭环

当前匹配报告能生成建议，但不能记录双方是否继续行动。

建议：
- 增加「申请连接」或「发起沟通」状态。
- 记录匹配后是否预约、是否收藏、是否完成交易。
- 后续用这些数据优化匹配排序。

### P2：后台仍是单 HTML 文件

短期适合内测，长期维护会变重。

建议：
- 内测期继续保留单文件后台。
- 当运营功能超过 10 个模块后，再迁移到正式管理端。

### P2：视觉一致性还需要真机截图复查

当前已经多轮优化，但微信开发者工具与真机字体渲染不同。

建议：
- 用 375px 宽度和真实手机分别检查：首页、找需求、找服务、找人、我的 Agent、匹配报告。
- 重点看按钮占比、卡片间距、长文本换行。

## 下一阶段方案

### 阶段 A：内测稳定性

目标：让 5-20 个真实体验者能顺利完成核心路径。

优先任务：
- 固定内测测试清单。
- 统一登录失效处理。
- 社区动态后台发布后首页展示。
- 修复内测反馈中的卡点。

验收标准：
- 新用户能登录。
- 能看首页动态。
- 能发布一个需求。
- 能浏览一个服务。
- 能查看一个 Agent。
- 能生成一次匹配报告。

### 阶段 B：需求中心重构

目标：把需求从个人档案附属内容升级为社区核心数据。

优先任务：
- 新增 `demands` 独立表。
- 新增需求 API。
- 我的 Agent 需求栏改为真实需求表读写。
- 找需求页面改为直接读取需求表。
- 后台需求管理改为直接管理需求表。

验收标准：
- 需求可筛选、可隐藏、可标记解决。
- 首页、找需求、公开 Agent 档案都能同步展示同一条需求。

### 阶段 C：服务结构化

目标：让服务像一个可理解、可预约、可交付的产品。

优先任务：
- 服务字段结构化：适合人群、交付物、案例、边界、不适合人群。
- 服务表单和后台表单统一字段。
- 服务详情页减少长段落，改为卡片化信息。

验收标准：
- 用户看服务详情 10 秒内能判断是否适合自己。

### 阶段 D：连接与匹配闭环

目标：匹配报告不只是报告，而是推动下一步行动。

优先任务：
- 增加关注 / 申请连接。
- 匹配报告加入下一步 CTA。
- 记录匹配后行为。
- 后台查看高分匹配与待跟进关系。

验收标准：
- 用户能从匹配报告进入一次真实行动。
